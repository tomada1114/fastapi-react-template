# Building Screens

**Owns:** how a screen is built under `frontend/src/`: where its route, feature, and
shared code go, how it reads and changes server data, how it renders an API error, its
styling and accessibility, and how its component tests drive it.
**Does not own:** where a test file goes and the coverage floor (`placing-tests`); how a
test case is written (`writing-tests`); the order of work, failing test first (`tdd`);
the route or schema on the API side (`building-api-routes`); the API's error shapes and
codes (`designing-errors`); adding a package (`managing-dependencies`); seeing the
screen against a running API (`running-the-app`); a lint, type, or coverage setting
(`changing-gates`). The toolchain, the generated files' mechanics, and the narrowest
checks are `frontend/AGENTS.md`'s.

## Where a screen lives

| What | Where |
|---|---|
| A route: one file per URL | `frontend/src/routes/` (`__root.tsx` is the layout, `index.tsx` is `/`) |
| The route tree | `frontend/src/routeTree.gen.ts`, generated from `src/routes/` by the router plugin; never edited by hand |
| A feature's components | `frontend/src/features/<feature>/`, exported through its `index.ts` |
| Code two features share | `frontend/src/lib/` (query client, Problem Details helpers) |
| The API client | `frontend/src/api/generated/`, generated by `just contract`; never edited by hand |
| The tests | `frontend/tests/`, mirroring `src/` (`frontend/AGENTS.md`'s "Tests and the coverage floor") |

- How the two generated trees are regenerated and staged is `frontend/AGENTS.md`'s
  "Routes, the generated client, and screens"; this skill does not repeat it.
- A route file stays thin: it declares the route and renders one feature component, so
  the feature can be tested without a router. Routes follow TanStack Router's file-based
  conventions: a file or folder whose name starts with `-` stays out of the route tree,
  and `$param` names a path parameter
  (https://tanstack.com/router/latest/docs/framework/react/routing/file-naming-conventions,
  checked 2026-10-13).
- The root route is made with `createRootRouteWithContext`, so a route's `loader` or
  `beforeLoad` reads the one `QueryClient` as `context.queryClient`. No route in the
  template has a loader yet.

## Server data

- **Server data only through the generated options.** Import them from
  `src/api/generated/@tanstack/react-query.gen` and spread them into the hook:
  `{operation}Options` (`queryOptions`) into `useQuery`, `{operation}InfiniteOptions`
  into `useInfiniteQuery`, `{operation}Mutation` into `useMutation`
  (https://heyapi.dev/openapi-ts/plugins/tanstack-query, checked 2026-10-13). No
  hand-written `fetch`, URL, or response type: a path, parameter, or body the contract
  does not have fails `tsc`.
- **A mutation invalidates the queries it changes**, in its `onSuccess` or `onSettled`.
  A generated query key is an array of one object whose `_id` is the operation name, and
  `queryKey: [{ _id: "<operation>" }]` matches every key of that operation, whatever its
  parameters, plain and infinite alike (observed in
  `frontend/tests/features/todos/CreateTodoForm.test.tsx`, 2026-10-13). Invalidate in
  `onSettled` when a failure can also mean the cache is stale. The to-do form
  invalidates `[{ _id: "listTodos" }]` after a create, and each to-do row on every
  settlement, so its loaded pages refetch from the first cursor even after a 404.
- **A paged list passes its own cursor rule** to `useInfiniteQuery`: the generated
  infinite options' `getNextPageParam` stops after one page, so the caller overrides
  it. The to-do screen passes `initialPageParam: {}` and reads `next_cursor`.
- **Server state lives in the TanStack Query cache, never in component state.** Read
  `query.data` where it is rendered; a `useState` copied from it goes stale on the next
  refetch.
- **Local UI state stays in the component** that owns it: a text field's draft, a
  pending flag, which notice is showing.
- **State that belongs in the URL goes in the route's search params** (a filter, a page,
  a selected tab), declared with the route's `validateSearch` and read with
  `Route.useSearch()`
  (https://tanstack.com/router/latest/docs/framework/react/guide/search-params, checked
  2026-10-13). The template has no route with search params yet.
- **The query client comes from `createQueryClient()`** in `src/lib/query-client.ts`.
  Its `shouldRetry` never retries a query whose error carries a 4xx `status` and retries
  anything else once; mutations keep TanStack Query's defaults, as every other option
  does. `main.tsx` creates one and hands it to both
  `QueryClientProvider` and `createAppRouter`. Change the policy there, never per screen.
- **The server is the validator.** Submit what the user typed, unchanged: no `required`,
  `maxLength`, or client-side rule that repeats one the API owns, and no form library.

## Rendering an API error

Every error a query or mutation throws goes through the Problem Details helpers in
`src/lib/`: `toApiError(error)` normalizes it to an `ApiError`, and
`<ErrorMessage error={...} />` renders it with `role="alert"`.

- `toApiError` returns `{ kind: "problem", status, title, detail?, code?, requestId?,
  fieldErrors }` for a Problem Details body, with `fieldErrors` keyed by the last
  element of each `errors[].loc` that starts with `body`. Anything else (a network
  failure, a body that is not Problem Details) is `{ kind: "unknown" }`.
- **A field error renders next to its input**, never only in a banner: the input gets
  `aria-invalid` and `aria-describedby` pointing at the message element, which has
  `role="alert"`. Read `fieldErrors[<field name>]` on a 422, and branch on `code`, not
  on `detail` text, for a domain 422 that names no field. The to-do form shows both the
  parsing 422's `fieldErrors.title` and the domain `invalid_todo` 422 under its title
  input.
- **Everything else renders through `ErrorMessage`.** For a 5xx it shows a generic
  message plus the request id when the body carries one; for `kind: "unknown"` (no
  response) a generic connection message, with no request id to show; for another 4xx,
  the body's `detail`, else its `title`.
- A screen that handles a code itself still parses the error with `toApiError` first.
  The to-do row reads `code === "todo_not_found"` on a 404 and reloads the list instead
  of showing an error.

## Styling

Tailwind CSS 4 utility classes in the markup are the only styling layer, through
`@tailwindcss/vite`. `src/styles.css` (`@import "tailwindcss";`) is imported by
`main.tsx` alone; a screen adds no stylesheet, CSS module, CSS-in-JS, or UI kit, and
Biome parses Tailwind's directives (`css.parser.tailwindDirectives`). Every
interactive element keeps a visible focus style. The sample's buttons use
`focus-visible:outline-2 focus-visible:outline-offset-2`. A design system, UI kit, form
library, or i18n is each app's own decision and a new package.

## Accessibility

Every screen passes the checklist in
[references/accessibility.md](references/accessibility.md) before it ships: a visible
label on every input, an accessible name on every button, focus moved to a defined
element after an item is removed, status and error messages announced, and every action
reachable from the keyboard.

## Testing a screen

A screen is tested by Vitest component tests under `jsdom` that render its feature
component and answer every request it makes with an MSW handler typed from the
generated types. **REQUIRED:** `placing-tests` for where the file goes and the
coverage gate, `writing-tests` for how each test is written: its `it` sentence,
Testing Library's query order with `getByRole` first, `userEvent.setup()`, the `jest-dom`
matchers, the MSW server's unhandled-request behavior, and waiting with `findBy...`.

- Render through `renderWithQuery`, and a route through `createAppRouter` with a memory
  history; the helpers are in
  [references/testing-screens.md](references/testing-screens.md).
- Cover each state the screen renders: loading, empty, data, a 422 next to its field, a
  5xx with its request id, and a network failure. The handler that produces each is in
  the same reference.

## Adding a screen

Take a hypothetical settings screen that reads `GET /api/settings` as the worked case:

1. The API side comes first: the route, its schema, and its tests. **REQUIRED:**
   `building-api-routes`. Then `just contract`; a route function named `get_settings`
   becomes the generated `getSettingsOptions`.
2. The tests, then the component, failing test first. **REQUIRED:** `tdd`. First
   `frontend/tests/features/settings/SettingsScreen.test.tsx` with MSW handlers for each
   state; see it fail with
   `pnpm --dir frontend exec vitest run tests/features/settings/SettingsScreen.test.tsx`;
   then `frontend/src/features/settings/SettingsScreen.tsx` and its `index.ts` until it
   passes.
3. The route: `frontend/src/routes/settings.tsx` with `createFileRoute("/settings")`,
   rendering `SettingsScreen`. The layout in `__root.tsx` has no navigation yet.
4. Check, from the repository root: `just frontend lint`, `just frontend test`, and
   `just frontend build` (`frontend/AGENTS.md` says what it regenerates). Run `just e2e`
   when a user flow changes, and `just contract-check` after an API change. Then
   `just verify` before the completion claim.
