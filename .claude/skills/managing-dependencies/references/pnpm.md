# The JavaScript side: pnpm

Read when adding, bumping, or removing a JavaScript package, or touching
`pnpm-workspace.yaml`. The sign-off and the review record in `SKILL.md` apply unchanged;
this file holds what differs for pnpm. The toolchain itself (Node.js 24, pnpm 11, how
both are fetched) is `frontend/AGENTS.md`'s "Toolchain".

## One workspace, one lockfile

- The root `package.json` pins pnpm and Node.js (`packageManager`, `devEngines`) and
  declares no dependency of its own. `pnpm-workspace.yaml` lists the members,
  `frontend` and `e2e`, and carries the supply-chain policy. One root `pnpm-lock.yaml`
  locks every member.
- Add from the repository root into the member that uses the package:
  `pnpm --dir frontend add <package>` for something the built screen imports (it lands
  in `dependencies`), `pnpm --dir frontend add --save-dev <package>` for a tool, a type
  package, or a test library, and `pnpm --dir e2e add --save-dev <package>` for the
  browser test. Never into the root `package.json`, and never by typing a version: under
  the window below, a hand-typed recent version may not resolve.
- A frontend `dependencies` entry is the runtime scope Dependency Review license-gates
  (`fail-on-scopes: runtime`), as `[project] dependencies` is on the Python side; a
  runtime package is also a design change (`AGENTS.md`'s "Before changing the
  architecture").

## Ranges

- `pnpm add` writes a caret range, `^X.Y.Z`, and `pnpm-lock.yaml` pins the exact
  version; no `save-prefix` is configured (`pnpm --dir frontend config get save-prefix`
  printed `undefined`, observed 2026-10-14). Keep the caret.
- **A pre-1.0 package is pinned exactly** (`pnpm add --save-exact`), since a 0.x minor
  may break: `@hey-api/openapi-ts` is `0.99.0`, and the client it generates is committed.
- **Two ranges are held to patches on purpose**, each with a Dependabot `ignore` entry
  in `.github/dependabot.yml` whose comment names its lift condition: `typescript`
  `~6.0.3` (7 crashes the generator) and `@types/node` `~24.19.0` (follows the Node.js
  runtime's minor, `.node-version`).

## `pnpm-lock.yaml`

- Generated by pnpm, never hand-edited, and committed in the same commit as the
  `package.json` that caused it. **BACKGROUND:** `smart-commit`'s "Group".
- `pnpm install --frozen-lockfile` (`just install`, `just frontend install`, and every
  CI job that installs) fails when a `package.json` and the lockfile disagree, and
  `verifyDepsBeforeRun: error` makes `pnpm exec` and `pnpm run` refuse a `node_modules`
  that no longer matches the lockfile: reinstall after the lockfile moves.
- The review record's transitive count is the `packages:` entries `pnpm-lock.yaml`
  gains, not only the direct one.

After any JavaScript dependency change:

```bash
just frontend lint && just frontend test && just frontend build   # a frontend package
just e2e-lint && just e2e                                          # an e2e package
just verify
```

## The window

The JavaScript side has the same 7-day window as `exclude-newer`: the root
`pnpm-workspace.yaml`'s `minimumReleaseAge: 10080`, an integer count of minutes (not a
duration string), with `minimumReleaseAgeStrict: true`, so `pnpm install` fails instead
of falling back to a younger version
(https://pnpm.io/settings/dependency-resolution, checked 2026-10-14), and
`trustLockfile: false` re-verifies every version already in `pnpm-lock.yaml`.
`.github/dependabot.yml`'s `npm` entry (pnpm's ecosystem; its one `directory: "/"`
covers every workspace member through the root lockfile) runs monthly with
`cooldown.default-days: 7`, grouped into `npm-minor-patch` and labelled like the `uv`
one; its `ignore` rules and their lift conditions are in its comments. One window holds
for the repository: `tests/harness/test_dependabot_cooldown.py` (`just check-harness`)
fails when the `npm` cooldown in minutes (days × 1440) differs from
`minimumReleaseAge`, when the `npm` and `uv` cooldowns differ, and when
`minimumReleaseAge` is missing or not an integer. Change all four values together, or
none; shortening any of them loosens a gate, which is the owner's decision.

- **Dependabot documents pnpm v7 to v10**
  (https://docs.github.com/en/code-security/dependabot/ecosystems-supported-by-dependabot/supported-ecosystems-and-repositories,
  checked 2026-10-14), and this repository runs pnpm 11, which works in practice. If a
  Dependabot `npm` job fails because of the pnpm version, record it (an issue with the
  job log, `triaging-issues`) and leave the pnpm version, the lockfile, and the policy
  as they are; never work around it.
- **A security update inside the window** skips Dependabot's cooldown, which applies
  to version updates only
  (https://docs.github.com/en/code-security/dependabot/working-with-dependabot/dependabot-options-reference,
  checked 2026-10-14), but not `minimumReleaseAgeStrict`: the install refuses the
  version, in the Dependabot job or the PR's CI. It waits out the window, or the owner
  decides the one-package exception below; never an implementer's call.

## Exceptions in `pnpm-workspace.yaml`

Every key below the member list is policy, and loosening one weakens a gate
(`changing-gates`). The keys that exempt something take reviewed entries. Each entry
is the owner's decision, made like a new package's sign-off, and carries a comment
saying what it exempts, why, and when it goes. The current entries' reasons live in
their comments; read them there rather than a copy here.

- **`minimumReleaseAgeExclude`**, the counterpart of `exclude-newer-package`: lets a
  security fix younger than the window install. pnpm accepts a package name (every
  version), a pattern, or specific versions, the last since pnpm 10.19.0
  (https://pnpm.io/settings/dependency-resolution, checked 2026-10-14). Name the one
  exact version, `<package>@1.2.3`, never a name or a pattern, which would exempt every
  later release too. The comment names the advisory, why waiting is riskier, and the
  removal date: the day that version turns 7 days old and the window admits it. Drop the
  entry once its date passes; `merging-dependency-prs`' review checklist looks for one.
  Never a shorter window to let one version through.
- **`allowBuilds`**: `strictDepBuilds: true` fails the install when a dependency has a
  build script not ruled on, and `allowBuilds` maps a package, optionally one version,
  to `true` (run it) or `false` (refuse it)
  (https://pnpm.io/settings/build, checked 2026-10-14). `false` when the package works
  without its script; `true` only with the owner's sign-off, like a new package. The
  review record of a new package names any script it wants.
- **`trustPolicyExclude`**: exempts a version from `trustPolicy: no-downgrade`, which
  fails a version whose trust level dropped from an earlier release
  (https://pnpm.io/settings/dependency-resolution, checked 2026-10-14).
- **`overrides`**: forces a version anywhere in the dependency graph
  (https://pnpm.io/settings/dependency-resolution, checked 2026-10-14), such as a
  transitive security fix the parent package has not taken yet.
- **`peerDependencyRules`**: `strictPeerDependencies: true` fails a command on a missing
  or invalid peer dependency, and `ignoreMissing`, `allowedVersions`, and `allowAny`
  each admit one anyway (https://pnpm.io/settings/peer-dependencies, checked
  2026-10-14). The template has none.
