# Smart Commit

**Owns:** turning a working tree into commits on the current branch — what goes in, how
it is grouped, the message, the recovery when a pre-commit hook refuses, and the push
when one is asked for. **Does not own:** opening or updating the pull request
(`create-pr`); shipping an issue end to end (`shipping-issues`); what the hooks run and
why (`changing-gates`); the order of work that produces a `src/` change (`tdd`).

A user-level skill of the same name may also be installed. Inside this repository,
follow this one: it is the one that knows these hooks.

**Invoking this skill is the sign-off for exactly the writes AGENTS.md's "Standing
exceptions" lists for it, for this invocation only:** the commits it makes on the
current branch, and — only when the request asked for a push — pushing that branch to
`origin`. Nothing else: no force-push, no amend of a pushed commit, no other branch, no
push of `main`.

## 1. State first

```bash
git branch --show-current
git status --short
git log --oneline -5
git diff --stat
git diff --cached --stat
```

- **On `main`:** stop and tell the requester to create a branch. The
  `no-commit-to-branch` hook refuses the commit anyway, and `.github/rulesets/main.json`
  requires a pull request into `main`.
- **Detached HEAD:** stop and ask; a commit there belongs to no branch.
- **A merge, rebase, or cherry-pick in progress:** read "When the hooks run" in
  [references/pre-commit-hook.md](references/pre-commit-hook.md) first, then commit a
  rebase resolution with `git commit` before `git rebase --continue`.
- **Something already staged** that you did not stage: it is the requester's. Ask before
  folding it into a group or unstaging it.

## 2. Decide what stays out

The mechanical list — `.env*`, `secrets/**`, a key file, personal agent settings, a
credential in a file's content — lives in `scripts/check_staged.py`, and the
`check-staged` hook refuses it at commit time. Do not restate it; what this step adds is
the judgment no pattern sees:

- A real key or token in an innocently named file — a fixture, a config, a log.
- Personal data in a fixture or a test expectation.
- Something the requester plainly did not mean to commit: a scratch file, a debug log, a
  build artifact `.gitignore` happens to miss, an
  editor's backup.

Judge a secret-shaped path by its name in `git status --short`, never by opening it.
Leave such a file unstaged and name it in the report.

## 3. Group

One commit per logical change: a reader of `git log` should be able to revert any one of
them without breaking another. Each is a Conventional Commit,
`<type>(<scope>): <summary>` — English, imperative, lower-case, no trailing period,
under 72 characters. Take the type and scope the way `create-pr`'s "Title" does, from
recent history (`git log --format=%s -40`).

These always move together, in the same commit:

| Change | Moves with | Because |
|---|---|---|
| A dependency in `pyproject.toml` | `uv.lock`, regenerated by `uv lock` | `just lock-check` and every `--locked` run refuse a lock out of step with its manifest. **BACKGROUND:** `managing-dependencies`, including the sign-off a new package needs. |
| `.agents/skills/<name>/` | `.claude/skills/<name>/`, from `just agents-sync` | `just agents-check` and CI refuse one tree without the other. **BACKGROUND:** `authoring-skills`. |
| A behavior change in `src/` or `scripts/` | Its test, and any document the change owes | A code-only commit lands untested behavior, and a later test can no longer be shown to have failed against it. **BACKGROUND:** `tdd`, `updating-docs`. |

If all the changes are one logical change, one commit is right; three related one-line
edits are one commit, not three. When two logical changes touch the same file, stage
hunks with `git add -p <file>` (or `git apply --cached <patch>` where nothing can
answer its prompts), then read the `ruff` and `ruff-format` rows of the recovery table
before committing.

## 4. Stage by name and commit

For each group, in dependency order:

```bash
git add <path> <path> ...
git diff --cached --stat
git commit -m "<type>(<scope>): <summary>"
```

- Stage by explicit path. Never `git add .`, `git add -A`, or `git commit -a`: each
  sweeps in whatever step 2 meant to leave out.
- Check `git diff --cached --stat` against the group before every commit; it is the last
  look before the hooks take theirs.
- A longer body goes in a file outside the checkout, passed with `-F <file>`, so the
  shell expands nothing in it.

## 5. When a hook refuses

Nothing was committed. Read which hook failed and follow its row in
[references/pre-commit-hook.md](references/pre-commit-hook.md), re-stage what the fix
touched by name, then run the same `git commit` again — a new commit, never `--amend` of
an earlier one.

Never `--no-verify` (or `-n`), never `SKIP=<hook id>`, never an edit to
`.pre-commit-config.yaml`, `scripts/check_staged.py`, `.check-staged-allow`, or
`.git/hooks/` to make this commit pass — save removing a `.check-staged-allow` entry
whose file this same change deleted or renamed, which narrows the exemption. AGENTS.md's
"Security and human approval" holds the prohibition; a refusal you cannot clear is a
stop, reported with the hook's output.

## 6. Push only when asked

```bash
git push -u origin <branch>
```

- Only when the request asked for a push, and only the current branch.
- A rejection as non-fast-forward stops: the remote has commits this checkout lacks.
  Never force-push past it.
- A pull request is `create-pr`'s; push here only when the request stops at the push.

## 7. Report

`git log --oneline origin/main..HEAD` (or the commits made, when there is no upstream),
whether anything was pushed and where, and every path left uncommitted with the reason.
